# Judge Game Comment Relevance

判断一组已经完成基础清理的游戏玩家评论，是否与用户本次指定的事件主题或研究问题相关。目标是保留能帮助研究该事件的评论，排除虽然来自同一游戏、但无法支持本次研究的内容。

本 Skill 只做相关性判断。不要验证评论真假，不要分析情绪，不要概括观点，不要折叠相似评论，也不要改写原文。

## 推荐输入规范

调用方通常提供：

1. **研究主题**：用户当前要研究的事件、争议或问题。
2. **评论集**：一个平台的一组评论，每条至少包含稳定的 `record_id` 和原始 `text`。标准输入可以同时包含上一步产生的 `hard_excluded` 与 `stats`，也允许包含其他预处理元数据。
3. **必要上下文**：只有在短句、代称或社区黑话无法仅凭评论理解时，才需要视频标题、帖子主题、角色名、版本名或事件简介。

研究主题必须具体到足以区分“同一游戏中的相关讨论”和“同一游戏中的其他讨论”。例如“研究《崩坏：星穹铁道》”过于宽泛；“研究新SP角色采用泳装形态是否引发制作诚意与付费价值争议”可以执行。

若研究主题仍无法确定核心对象和纳入范围，可以提出一个合并后的澄清问题；若当前运行不允许追问，则按已提供内容作保守判断，并在可用的输出元数据中提示主题边界不足。不要因此循环重试。

## 输出约定

读取 [references/io-reference.md](references/io-reference.md) 了解推荐接口。模型在内部判断哪些评论相关，但最终结果不是判定表：

- `comments` 只保留与研究主题相关的评论。
- 每条保留原始 `record_id` 和 `text`，不输出 `decision`、分数或理由。
- 不相关评论直接从最终 `comments` 中移除，不另行列出全文。
- 输入已有的 `hard_excluded` 可以原样保留，表示前置空文本、损坏记录等确定性排除；不要把相关性排除项追加进去。
- 在 `stats` 中留下本步处理数量，包括相关性判断前的候选数、因不相关移除数和最终保留数。

推荐输出沿用输入外壳，但这是一种接口约定，不是触发重试的严格 Schema。若实际输入增减了字段、字段顺序不同或附带额外元数据，直接识别可用内容并完成一次筛选，不要要求调用方把输入改成逐字一致的模板，也不要因为外壳差异自我重试。

本 Skill 的硬要求只限于语义：不得改写被保留评论的 `record_id` 和 `text`，不得把明显无关评论留在结果中。顶层字段数量、字段顺序、统计字段的具体名称和是否存在都不是硬校验条件。

## 工作流程

### 0. 执行方式：脚本预筛 + 模型精筛（两级）

- 允许先用关键词/正则脚本做第一遍粗筛，把每条评论标记为候选保留或候选排除，并生成 `record_id` 清单供模型复核。脚本只用于缩小范围、降低遗漏，不作为最终判断。
- 无论脚本给出什么结果，模型必须逐条语义复核全部评论（含脚本标记为「候选排除」的），以模型判断为最终结果。脚本预筛命中率低或主题特殊时，直接全部交给模型判断。
- 不把脚本的排除清单直接当作结论输出；脚本建议与模型结论不一致时，以模型为准。

### 1. 宽松识别输入而不重新清洗

- 优先读取 `platform`、`comments`、`hard_excluded` 和 `stats`。
- `comments` 中通常以 `record_id` 和 `text` 表示一条评论；只要语义清楚，可容忍额外字段及字段顺序变化。
- 保留原顺序，不重新编号。
- 只遍历 `comments`；对其中每条候选评论在内部作出保留或排除判断。
- 不修正错别字、表情、标点、空格或社区黑话。
- `hard_excluded` 表示上一步已经确定排除的记录，不重新判断、不移回 `comments`。
- `stats` 是上一步的处理摘要，不把其中的数量或字段当作评论内容，也不据此推断相关性。

如果个别候选记录缺少可识别的编号或正文，不要反复要求重新输入，也不要重新启动整批任务；在当前输出允许的情况下保留该记录并提示无法判断，否则跳过该损坏记录并完成其余评论。`hard_excluded` 中记录空文本属于正常输入。

### 2. 冻结本次相关性框架

在逐条判断前，先在内部明确四项内容，并在整批评论中保持不变：

1. **核心对象**：具体角色、版本、剧情事件、玩法、运营事件或系统问题。
2. **核心问题**：用户究竟想研究什么判断，例如强度膨胀、角色制作诚意、抽取成本、剧情塑造或技术故障。
3. **允许的关联路径**：哪些相邻话题能够解释事件的原因、表现、影响、玩家诉求或行为意向。
4. **明确排除范围**：同一游戏中哪些话题不回答当前问题。

不要在处理后面的评论时临时放宽或缩窄标准。对同类表达使用同一判断口径。

### 3. 选择相关主题参考

用户整理的参考案例位于 [references/hsr-related-examples.md](references/hsr-related-examples.md)。它是帮助理解相关性边界的示例集，不是来源档案或事实证据库。只读取与本次主题匹配的章节；跨主题事件可读取多个相关章节，但不要把全部示例无差别塞入当前判断。

可选主题包括：

| 主题 | 标识 | 适用内容 |
|---|---|---|
| 角色强度 | `character_power` | 伤害、生存、配队、命座体验、就业空间、关卡表现 |
| 剧情 | `story` | 叙事质量、节奏、角色动机、设定表达、人物塑造 |
| 数值膨胀与版本环境 | `power_creep_environment` | 新旧角色迭代、怪物数值、环境抬角、保值率、版本主推 |
| 氪金与抽卡压力 | `monetization` | 抽数、保底、命座与专武成本、月卡、零氪微氪体验 |
| 角色制作投入 | `character_production` | 建模、美术、动作、演出、配音、音乐、角色设计与制作诚意 |
| 玩法与内容 | `gameplay_content` | 活动、地图、解谜、常驻模式、可玩性、内容空档 |
| 养成与资源体验 | `progression` | 遗器、体力、材料、养成周期、肝度、资源获取 |
| 功能、技术体验与运营 | `technical_operations` | Bug、性能、登录、UI、功能便利性、版本节奏与运营回应 |

这些类别是参考路由，不是固定标签体系。用户可以研究未列出的游戏主题；此时根据研究问题本身建立相关性框架，不要强行归入最接近的类别。

### 4. 理解示例的正确含义

参考文档只有正例：

- `R` 是明确相关正例。
- `B` 是参考集中已经标注为纳入该主题的边界相关正例。
- `B` 不表示“不确定”“需要审核”或“不相关”。
- 同一句可以在不同研究主题中同时相关。
- 案例中的 ID 只用于区分示例，不需要复制到实际输出。
- 案例只说明什么内容可以纳入对应主题；不要把示例中的玩家说法当作官方事实，也不要把示例当成必须逐字匹配的关键词库。

从示例中学习“关联路径”和“边界如何被纳入”，不要把角色名、术语或关键词复制成机械词表。示例来自《崩坏：星穹铁道》，但判断原则应迁移到其他游戏。

### 5. 逐条判断

按以下顺序判断每条评论。

#### A. 确认评论在谈什么

优先使用评论原文。只有当研究任务同时提供了视频标题、帖子标题、事件简介或角色上下文时，才可用这些上下文解析“她”“这个版本”“小鸟”“天气之子”等代称和社区黑话。

不得凭空补全没有提供的上下文。评论提到同一款游戏，不等于与本次事件相关。

#### B. 判断是否存在有效关联并保留

满足以下任一条件可在最终 `comments` 中保留：

1. **直接相关**：评论直接评价、描述、询问或建议研究主题中的核心对象与核心问题。
2. **结果相关**：评论描述该事件导致的体验、态度、付费、抽取、回流、退游、传播或其他行为意向。
3. **原因相关**：评论从强度、版本环境、剧情、美术、玩法、资源、技术或运营等方面解释事件为何发生或为何引发反应。
4. **边界相关**：评论同时涉及多个主题，但其中至少一条含义能够真实回答本次研究问题。
5. **反向意见**：评论否认、反驳或弱化事件中的主流批评，但仍在回答同一个研究问题。

相关性不等于赞同，也不等于事实正确。正面、负面、中立、激烈、少数、反驳性和未经核实的评论使用同一相关性标准。

#### C. 判断是否应从结果中排除

满足以下任一条件从最终 `comments` 中移除：

1. 讨论的是同一游戏中的另一个话题，且没有解释本次事件的原因、表现、影响或玩家行为。
2. 只出现角色名、游戏名、版本名或相关关键词，但没有形成与研究问题的语义联系。
3. 主要内容是无关的个人生活、@他人、站外闲聊或其他对象。
4. 只凭缺失的画面、上文或圈内语境才能猜测关联，而且任务没有提供足够上下文。
5. 内容虽然有观点，但该观点不能回答本次研究主题。

不要因为评论短、口语化、有错别字、含表情或使用社区黑话就排除。只要对象和关联明确，“加强景元”“0+0即毕业”“这版本长草了”都可能是有效相关评论。

#### D. 二分类如何处理边界

本 Skill 不输出人工复核状态或判断标签。遇到边界表达时：

- 若提供的研究主题和上下文足以建立真实、可说明的关联，保留。
- 若必须发明缺失对象、推测反讽方向或假设不存在的因果关系才能纳入，排除。
- 不得通过添加置信度、第三种标签或自由解释来逃避二分类。

优先避免把明确相关的少数意见、反驳意见和跨主题原因链误删；但不要因为评论来自预先筛选的视频，就默认全部保留。

### 6. 生成结果

- 只复制被保留评论的 `record_id` 和 `text`，不添加 `decision`。
- 保持被保留评论在输入中的相对顺序，不重新编号。
- 默认输出可解析 JSON；如果调用节点明确要求其他承载方式，则遵循节点要求。
- 默认沿用输入的顶层结构，并原样保留 `hard_excluded` 与其他预处理元数据；不要为这些已排除记录生成相关性结论。
- 在 `stats` 中保留已有的预处理统计，并补充：`relevance_input_count`、`relevance_excluded_count`、`final_kept_count`。若调用方使用等价字段名，也可沿用其命名。
- 三项数量满足：`relevance_input_count = relevance_excluded_count + final_kept_count`。
- 输出格式服务于机器传递，但格式约束不替代语义判断；必须依据研究主题独立判断每条评论，而不是照抄示例标签或按关键词机械筛选。
- 一次完成当前批次。不要因为顶层字段、字段顺序、统计字段或示例外壳不完全一致而再次调用模型、再次调用工具或重新处理同一批数据。

## 大批量评论

当评论集过大、无法在一次调用中可靠处理时，可以分批，但必须：

1. 先冻结同一份研究主题和相关性框架。
2. 每批保持原始顺序和互不重叠的编号。
3. 不因不同批次改变判断标准。
4. 合并时只汇总各批保留项，并累加相关性输入数、排除数和最终保留数。
5. 最终输出一个可解析的 JSON 对象；默认保持输入外壳，也可以遵循调用节点明确提供的兼容外壳。

不要为了缩短输出而遗漏评论，也不要抽样代替逐条判断。

## 完成前自查

提交前快速检查核心信息，不把检查失败转化为循环重试：

- `platform` 与输入一致。
- 输出 `comments` 只含相关评论。
- 每个保留的 `record_id` 存在、唯一，相对顺序不变。
- 每段被保留的 `text` 与输入逐字一致。
- 输出评论没有 `decision`、相关性分数或理由字段。
- `hard_excluded`、`stats` 及其他预处理元数据没有被误判为评论或擅自改写。
- 相关性输入数等于相关性排除数与最终保留数之和。
- 没有根据立场、热度或事实真假改变相关性。
- 没有把同一游戏中的其他话题自动当作相关。
- 没有把参考文档中的 `B` 样本误判为待审核项。

若能在当前响应中直接修正重复编号、原文变化或统计差异，则修正一次后提交；不要为追求模板完全一致而重新发起整轮处理。

## 边界

- 输入应是完成空文本和明显机器噪声处理后的评论集；已排除项可以作为 `hard_excluded` 随文件传入。原始爬虫响应不属于本 Skill。
- 不执行网页搜索，不调用社媒采集接口，不补充外部证据。
- 不核验玩家陈述，不把相关评论升级为客观事实。
- 不做情绪、立场、观点聚类、相似折叠或最终运营结论。
- 不跨平台合并数据；每个平台分别判断并保留自身 `platform`。
